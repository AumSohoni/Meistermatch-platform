# CHAPTER 5: PRACTICAL / PROJECT PART

## 5.1. System architecture overview

The proposed Tinder-style platform for matching skilled workers with employers in Latvia follows a mobile-first, cloud-based architecture. The system is designed to handle user registration, profile management, geolocation-based matching, swipe mechanics, mutual-match detection, rating systems, and secure messaging.

### 5.1.1. High-level architecture components

| Layer | Technology | Function |
|-------|-----------|----------|
| **Presentation** | React Native (cross-platform) or Flutter | Mobile frontend for iOS and Android; provides native-like experience with swipe gestures, geolocation, and push notifications |
| **Application Logic** | Node.js with Express OR Go with Gin | Backend server handling API requests, authentication, swipe engine logic, match management, and rating calculations |
| **Database** | PostgreSQL with PostGIS extension | Relational data storage for users, profiles, matches, ratings, and messages; PostGIS for geospatial queries (radius search) |
| **Cache/Real-time** | Redis | Fast state persistence for swipe decisions, online user status, and real-time match notifications via WebSockets |
| **File Storage** | Amazon S3 / Google Cloud Storage | Store user-uploaded certificates, profile photos, and demonstration videos |
| **AI/Recommendation** | TensorFlow Lite (on-device) or lightweight Python service | Basic collaborative-filtering + content-based filtering on skill-badges, location, and salary preferences |
| **Messaging** | Firebase Cloud Messaging (FCM) | Push notifications for new matches and messages; end-to-end encryption via Signal protocol integration |
| **GDPR Compliance** | Consent management module | Explicit opt-in for data processing, right-to-erasure endpoints, data-minimisation defaults |

### 5.1.2. Data flow diagram (simplified)

1. **User onboarding** → Registration → Profile creation (trade, certs, location, preferences)
2. **Profile data** → Stored in PostgreSQL + skill-badges indexed
3. **Geolocation input** → Latitude/longitude stored; PostGIS calculates radius searches
4. **Swipe action** → Frontend sends swipe direction to backend → Redis updates user state → Backend checks mutual match condition → If matched → unlock chat
5. **AI recommendation** → Backend serves next profile card based on preference vector + collaborative filtering
6. **Trial shift & rating** → Post-trial, both parties rate each other (1-5 stars) → Ratings stored → Average rating exposed on profile
7. **Messaging** → Mutual match triggers chat unlock → End-to-end encrypted messages via Firebase

### 5.2.3. Skill-badge system

- **Badge schema**: `{code: string, name: string, issuer: string, year: integer, verification_url: text}`
- **Common construction badges**: 
  - `EWPA` – European Woodworking Platform Welder certification
  - `CPCS` – Construction Plant Competence Scheme (excavator/loader operator)
  - `City & Guilds` – Vocational qualification levels 1-3
  - `OSHA 10/30` – Occupational safety certification (US, but accepted internationally)
  - `RG certification` – Latvian building code compliance
  - `Green Card` – Site safety passport (common in EU construction)
- **Verification**: Certificates uploaded as PDF → OCR extraction → stored in S3 → verification URL generated → badge displays "verified" status on profile card
- **Badge display**: Small icon on profile card; clicking reveals full details and verification link

## 5.3. Geolocation and radius search

### 5.3.1. Implementation

- **Coordinates storage**: Both employer and worker profiles store `POINT(latitude, longitude)` using PostGIS
- **Radius search query**: 
  ```sql
  SELECT * FROM users 
  WHERE ST_DWithin(
    employer.location, 
    worker.location, 
    :radius_km * 1000  -- convert km to meters
  )
  AND employer.trade_specialisation = worker.trade_specialisation
  ```
- **User control**: 
  - "Show me within 50km of Riga"
  - "Willing to relocate – show all Latvia"
  - "Hide my exact location; show only region"
- **Consent mechanism**: GDPR-compliant location permission request on first app launch; option to use city-level instead of exact coordinates

### 5.3.2. Geofencing for trial shifts

- When a mutual match occurs, the system can suggest nearby trial-shift locations
- Employer can set "trial zone" – e.g., "only candidates within 30km"
- Worker receives notification if they enter the trial zone
- Supports on-site short-term project matching

## 5.4. Swipe engine and mutual-match logic

### 5.4.1. Swipe mechanics

- **Card display**: Each card shows truncated profile: trade, 1-2 skill badges, distance, pay indication, rating stars
- **Swipe actions**: 
  - Right = "Interested" (like)
  - Left = "Not interested" (dislike)
  - Up = "Super-like" (premium feature)
  - Down = "Pass"
- **State persistence**: 
  - Local storage on device for offline swipe history
  - Backend Redis cache for real-time sync across devices
  - Database table `swipes(user_id, candidate_id, direction, timestamp)` for audit and analytics

### 5.4.2. Mutual-match algorithm

```
Algorithm: mutual_match(user_id, candidate_id)
1. Check if both users have swiped right on each other:
   - Query DB: SELECT * FROM swipes 
     WHERE (user_id = A AND candidate_id = B AND direction = 'right')
       OR (user_id = B AND candidate_id = A AND direction = 'right')
2. If both right-swipes exist AND not already matched:
   - Insert record INTO matches(user_id=A, candidate_id=B, matched_at=NOW())
   - Unlock chat functionality for both parties
   - Send push notifications to both users
3. If only one right-swipe:
   - Store the swipe for future reference
   - Do NOT unlock chat
   - Continue swipe feed
4. If no right-swipes:
   - Return to step 1 on next profile presentation
```

### 5.4.3. Swipe fatigue prevention

- After 20 swipes in 15 minutes, suggest a break
- AI recommendation every 5th card based on preference learning
- "Reset swipes" daily – old swipes expire after 24 hours
- "Hide shown profiles" option – users can mark profiles they've seen

## 5.5. AI recommendation engine

### 5.5.1. Preference learning model

The system learns user preferences from swipe behavior to improve match quality over time.

**Feature vector per profile**: `[trade_encoded, years_experience, certification_count, pay_min, pay_max, location_distance, rating]`

**Preference vector per user**: Updated after each swipe using simple gradient descent:
- If swipe right → increase weight for matching features
- If swipe left → decrease weight

**Algorithm**: 
1. **Content-based filtering**: Match profiles where `trade_specialisation` matches user's most-swiped trade, and certification overlap > 50%
2. **Collaborative filtering**: Anonymised swipe-pattern analysis – if users with similar swipe history to User X also swiped right on Candidate Y, suggest Candidate Y to User X
3. **Hybrid approach**: 70% content-based + 30% collaborative filtering for new users (cold start)

### 5.5.2. Implementation options

- **On-device (TensorFlow Lite)**: Low latency, preserves privacy, works offline; model size ~200KB
- **Backend service (Python/Flask)**: More complex models, requires internet connection, can handle larger datasets
- **Recommended for MVP**: On-device lightweight model with monthly preference vector sync to backend for aggregate analytics

### 5.5.3. Cold-start solution

- New users complete a "preference setup" questionnaire (trade, salary range, max distance, certifications)
- Initial recommendations based on questionnaire + matching with profiles having those exact attributes
- After 10 swipes, ML model begins learning from actual behavior

## 5.6. Rating and review system

### 5.6.1. Rating schema

| Field | Type | Description |
|-------|------|-------------|
| `rating_id` | UUID | Primary key |
| `rater_id` | UUID | User who gives the rating (employer or worker) |
| `ratee_id` | UUID | User who receives the rating |
| `shift_date` | Date | Date of completed trial shift |
| `rating_value` | Integer (1-5) | star rating |
| `comment` | Text (max 500 chars) | Free-form feedback |
| `related_match_id` | UUID | Link to the match that produced this trial |
| `created_at` | Timestamp | When rating was submitted |
| `is_public` | Boolean | Whether rating visible on public profile (default: true) |

### 5.6.2. Rating calculation

- **Simple average**: `AVG(rating_value)` over all public ratings for a user
- **Weighted average**: New ratings weighted higher using exponential decay:
  `weight = e^(-days_since_shift / 90)` – recent ratings matter 3x more than year-old ratings
- **Minimum sample size**: At least 3 ratings required before average displays on profile
- **Outlier handling**: Ratings outside 1-5 range rejected; extreme values (>4 std dev from mean) flagged for review

### 5.6.3. Rating badges

- **5.0 stars**: "Elite performer" badge on profile
- **4.5+ stars**: "Highly recommended" badge
- **3.5-4.4 stars**: "Reliable" badge
- **Below 3.5 stars**: No special badge; system suggests skill development resources

### 5.6.4. Dispute resolution

- If either party disputes a rating, they can submit a flag
- Admin review within 48 hours
- Disputed ratings temporarily hidden; if upheld, rating removed; if rejected, rating stands with note

## 5.7. Secure messaging

### 5.7.1. Architecture

- **Mutual match triggers**: When `matches` table records a mutual right-swipe, the chat API endpoint becomes accessible
- **End-to-end encryption**: 
  - Signal Protocol implemented via library (e.g., `swrve`, `signal-node`)
  - Keys generated per chat session; stored only on client devices
  - Server forwards encrypted messages; cannot read content
- **Message TTL**: Messages auto-delete after 30 days (configurable); users can manually delete
- **Typing indicators**: Via WebSocket keep-alive; no message content exposed to server

### 5.7.2. Features

| Feature | Description |
|---------|-------------|
| **Pre-filled tags** | Match screen suggests: "Available this week?", "Trial shift 4h?", "Relocation willing?" |
| **Quick replies** | Canned responses: "Interested", "Available Monday", "What's the pay?" |
| **File sharing** | Share certificate photos, within 5MB limit, encrypted |
| **Block/report** | User can block/unmatch; report rating or behavior to admin |
| **Offline messaging**: Store messages server-side until user reconnects; FCM push notification when new message arrives |

### 5.7.3. GDPR compliance in messaging

- All messages linked to `match_id`; no personal data in message payload beyond what's necessary for the conversation
- Right to erasure: User can request deletion of all messages related to a specific match
- Data processing agreement: Clear statement in onboarding about message storage (30-day TTL, encrypted)

### 5.9.2. Database schema (key tables)

```sql
-- Users table (inherited by employers and workers via role column)
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    role VARCHAR(50) CHECK (role IN ('employer', 'worker', 'admin')),
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    gdpr_consent BOOLEAN DEFAULT FALSE,
    location_consent BOOLEAN DEFAULT FALSE
);

-- Profiles table (one-to-one with users)
CREATE TABLE profiles (
    id UUID PRIMARY KEY REFERENCES users(id),
    trade_specialisation VARCHAR(100) NOT NULL,
    years_experience INTEGER,
    certifications JSONB,  -- JSON array of badge objects
    location POINT,  -- PostGIS point, nullable for privacy mode
    desired_pay_min NUMERIC,
    desired_pay_max NUMERIC,
    availability VARCHAR(50),
    rating_average NUMERIC DEFAULT 0,
    rating_count INTEGER DEFAULT 0,
    photo_url TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Swipes table
CREATE TABLE swipes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id),
    candidate_id UUID REFERENCES users(id),
    direction VARCHAR(10) CHECK (direction IN ('right', 'left', 'up', 'down')),
    timestamp TIMESTAMP DEFAULT NOW(),
    UNIQUE(user_id, candidate_id)
);

-- Matches table (mutual right-swipes)
CREATE TABLE matches (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    employer_id UUID REFERENCES users(id),
    worker_id UUID REFERENCES users(id),
    matched_at TIMESTAMP DEFAULT NOW(),
    trial_shift_scheduled BOOLEAN DEFAULT FALSE,
    trial_shift_date DATE,
    completed BOOLEAN DEFAULT FALSE,
    UNIQUE(employer_id, worker_id)
);

-- Ratings table
CREATE TABLE ratings (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    rater_id UUID REFERENCES users(id),
    ratee_id UUID REFERENCES users(id),
    shift_date DATE,
    rating_value INTEGER CHECK (rating_value BETWEEN 1 AND 5),
    comment TEXT,
    related_match_id UUID REFERENCES matches(id),
    created_at TIMESTAMP DEFAULT NOW(),
    is_public BOOLEAN DEFAULT TRUE
);

-- API rate limiting and audit logs
CREATE TABLE api_logs (
    id SERIAL PRIMARY KEY,
    user_id UUID REFERENCES users(id),
    endpoint VARCHAR(255),
    request_method VARCHAR(10),
    status_code INTEGER,
    response_time_ms INTEGER,
    timestamp TIMESTAMP DEFAULT NOW()
);
```

## 5.10. Prototype demonstration

The MVP prototype implements the following core functionality:

1. **User registration & onboarding**: Email/login; GDPR consent collection; location permission request; trade specialization selection from dropdown (carpentry, electrical, masonry, welding, plumbing, painting, roofing)
2. **Profile creation**: Upload profile photo; enter years of experience; list certifications (manual entry + OCR upload); set desired pay range; availability; willingness to relocate
3. **Swipe feed**: Continuous card feed showing: trade, 2 skill badges, distance (km), desired pay, rating stars (if ≥3 ratings); swipe right/left/up/down controls
4. **Mutual match detection**: When both users swipe right → system unlocks chat; push notification sent to both parties
5. **Basic chat**: End-to-end encrypted messaging with pre-filled tags; message TTL 30 days
6. **Rating system**: After marking trial shift as "completed", both parties rate each other (1-5 stars); average displays on profile after 3 ratings
7. **Geolocation filter**: Slider to set max distance (5km–100km); toggle "willing to relocate"
8. **Admin dashboard (basic)**: View total users, matches per day, rating distribution; export CSV

**Technical limitations of MVP**:
- No AI recommendation engine (profiles served in random order from nearby radius)
- No payment integration (premium features disabled)
- No external system integration (EURES, SDA)
- Simplified certificate verification (manual entry only)
- Single-language UI (Latvian/English toggle only)

**Prototype tech stack used**: 
- Frontend: React Native 0.73 + TypeScript
- Backend: Node.js 20 + Express + TypeScript
- Database: PostgreSQL 15 with PostGIS via Supabase free tier
- Storage: Supabase Storage (S3-compatible)
- Authentication: Supabase Auth (JWT)
- Deployment: Vercel (frontend), Supabase (backend + DB)

**Evaluation plan**: 
- Usability testing with 2 SME employers and 2 skilled workers (Riga area)
- Metrics: time to first match, swipe completion rate, chat engagement, rating submission rate
- Feedback collection: SUS (System Usability Scale) questionnaire
- Iteration: Incorporate top 3 pain points into Version 2 prototype
